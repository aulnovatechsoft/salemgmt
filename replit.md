# BSNL Sales & Task App
A mobile-first application for managing task assignments and tracking performance for BSNL (Bharat Sanchar Nigam Limited) with web deployment support.

## Run & Operate
- **Run migrations**: `bun run backend/db/migrate.ts` (this is the only command needed — review-snapshot and notification-enum sync run automatically as part of it; the standalone scripts still exist for ad-hoc reruns)
- **Build web**: `bunx expo export --platform web`
- **Start server**: `bun run server.ts`
- **Env Vars**:
    - `BSNL_DATABASE_URL`: PostgreSQL connection string.
    - `GEO_FENCE_KM`: Soft geo-fence radius in km (default `50`).
    - `GEO_FENCE_ENFORCE`: `soft` (log + allow) or `hard` (reject).
    - `EXPO_PUBLIC_GPS_TEST_MODE`: When `1`/`true`/`on`, web GPS capture returns Bharat Sanchar Bhawan (28.6259, 77.2088) instead of calling `navigator.geolocation`, and screens render an orange "TEST MODE" banner. Lets the QA team test web flows without HTTPS / real GPS. **MUST be unset (or `0`) for production builds** — the value is baked into the JS bundle at build time.

## Stack
- **Frontend**: React Native, Expo SDK 54, React Native Web
- **Backend**: Hono, tRPC
- **Database**: PostgreSQL (via Drizzle ORM)
- **State Management**: Zustand, React Query
- **Styling**: React Native StyleSheet

## Architecture decisions
- **"Task" Terminology**: Consistently uses "Task" instead of "Event" across the application for clarity.
- **Finance Collection Workflow**: Implements a strict submit→approve/reject lifecycle for finance entries with transaction-level safeguards against race conditions and data integrity.
- **Geo-fencing**: Enforces location-based submission validation with soft and hard limits, dynamically calculating anchors from prior entries.
- **Audit Logging & Notifications**: Critical actions trigger audit logs and best-effort notifications (logged but not blocking core transactions) for resilience.
- **Hierarchical Data Access**: Analytics and reports use `getVisibleEmployeeIdsSubquery` to enforce data visibility based on employee hierarchy and roles.
- **IST-correct Daily Bucketing**: Database aggregations are time-zone aware (`AT TIME ZONE 'Asia/Kolkata'`) to ensure accurate daily data alignment regardless of server timezone.

## Product
- **Task Management**: Create, assign, and track various task categories (Sales, O&M, Finance).
- **Sales & Marketing (S&M) Submission**: Guided flow for submitting sales data, including geo-fencing and photo uploads.
- **Finance Collection**: Workflow for submitting, approving, and rejecting financial collections with robust validation.
- **Operations & Maintenance (O&M) Entry**: Dedicated workflow for recording maintenance activities with photo and location.
- **Hierarchy & Reporting**: Comprehensive employee hierarchy system with CSV import, and multi-tier analytics dashboards for sales, O&M, and finance.
- **Real-time Notifications**: System for push and in-app notifications for task assignments, status changes, issues, and subtasks.
- **Resource Management**: Tracks SIM and FTTH inventory from circle allocation to individual sales.
- **Admin Tools**: Bulk task upload via CSV, privileged user management, and executive task console for national overview.
- **Automated Task Status**: Tasks automatically complete based on end dates, with a scheduled sweep to ensure accuracy.

## Gotchas
- **Photo Uploads in Native Builds**: `EXPO_PUBLIC_API_BASE_URL` must be set to an HTTPS URL for native builds; local development works with `localhost` over HTTP.
- **GPS capture (all submission screens)**: For the screen-level location state (the value that gets sent to the backend on submit), ALWAYS go through `captureLocation()` in `lib/captureLocation.ts`. The helper centralises four production-critical guarantees: (1) HTTPS / secure-context detection (geolocation is silently blocked on `http://` origins by all modern browsers, returns generic PERMISSION_DENIED with misleading guidance); (2) error-code-to-actionable-message mapping; (3) preemptive-prompt avoidance — auto-capture on mount must pass `{ onlyIfAlreadyGranted: true }` so the OS/browser permission prompt only fires from an explicit user button press; (4) runtime Null Island guard — coordinates exactly at (0, 0) are rejected as `INVALID_COORDS` regardless of source, so a buggy browser/device/mock can never silently slip past the geo-fence. The original regression: an earlier `if (Platform.OS === 'web') setLocation({lat:'0', lon:'0'})` shortcut silently lied to users with a "Location Captured ✓" pill while every web submission was hard-rejected by the backend geo-fence (~9000 km from any real BSNL circle anchor). Note: it is acceptable for native photo-capture flows (`takePhoto` / `pickImage`) to call `Location.getCurrentPositionAsync` directly for a fresher per-photo geo-tag — that's a non-blocking refresh on top of an already-validated `currentLocation`, never a substitute for it.
- **O&M Undo Gap**: Undoing O&M progress decrements the counter but doesn't delete `maintenance_entries` rows, leading to potential drift (P2 to address).
- **Status Backdoor Closed**: Direct status changes via `events.update` are stripped; all status transitions must use `updateEventStatus` for proper state machine, auditing, and notifications.
- **`GEO_FENCE_KM * GEO_FENCE_HARD_MULT`**: Submissions beyond this hard limit (default 150km) are always rejected.
- **`Alert.alert` confirm on RN Web**: The "Submit" button inside an `Alert.alert([...buttons])` modal is unreliable on web — the press handler frequently never fires, so the mutation silently never runs. For any confirm-then-submit flow that ships to web, branch on `Platform.OS === 'web' ? window.confirm(msg) : Alert.alert(...)` (see `app/event-detail.tsx` Submit-for-Review button). Otherwise users see the dialog, tap Submit, and nothing happens — no error, no log line, no DB write.
- **`notification_type` Postgres enum drift**: Three sources must stay in sync — the `NotificationType` TS union (`backend/services/notification.service.ts`), the `NOTIFICATION_TYPES` tuple (`backend/trpc/routes/notifications.ts`, drives Zod validation + the prefs UI), and the Postgres `notification_type` enum. If a TS value is missing from the DB enum, `createNotification`'s INSERT throws, the try/catch swallows it, and the recipient's bell stays empty with no user-visible error. Adding a new type now requires: (1) extend the TS union, (2) add to `NOTIFICATION_TYPES` tuple, (3) add to `REQUIRED_NOTIFICATION_TYPES` in `migrate-notification-enum.ts` so the next `migrate.ts` run picks it up. Always prefer a typed helper (e.g. `notifyFinanceCollectionSubmitted`) over raw `db.insert(notifications)` so the type system catches drift at compile time. Original failure: `TASK_SUBMITTED`, `TASK_APPROVED`, `TASK_REJECTED`, `SLA_WARNING`, `SLA_BREACHED` were referenced from code but absent from the enum, so every Submit-for-Review notification silently failed.
- **Task completion is gated on per-assignee approval (Phase 1)**: A task can only transition `active|paused → completed` when EVERY `event_assignments` row with a non-zero target sum has `submission_status='approved'`. Three places enforce this and must stay in sync: (1) UI in `app/event-detail.tsx` — the readiness panel above the action buttons + the disabled Complete button (driven by `completionReadiness` and `renderAssigneeStatusPill`); (2) `updateEventStatus` in `backend/trpc/routes/events.ts` — a friendly pre-tx probe (BAD_REQUEST with "X of Y still need approval") followed by an atomic `NOT EXISTS (...)` clause inside the same CAS UPDATE that flips status, with a re-query inside the tx to disambiguate "approval race" vs "status race"; (3) `_completeExpiredEventsCore` (the auto-complete sweep) — both pre-filters by per-event `pendingByEvent` count AND adds the same atomic `NOT EXISTS` clause to its own batch UPDATE. The pre-filter alone is not enough — a concurrent un-approve between the SELECT and the UPDATE would slip through. The `force` field on `updateEventStatus` is reserved for Phase 2 (force-complete-with-reason); until that ships with role gating + reason validation + audit, the server throws `FORBIDDEN` immediately if `input.force` is truthy. Reopens (`cancelled → completed` via admin) are intentionally exempt because the original work was already done. Empty-target placeholder rows (the manager-self entry sometimes injected by the team builder) are correctly skipped on both client and server because their target sum is 0.
- **Never prefix `AND ` inside a `sql\`...\`` fragment that is passed to Drizzle's `and(...)` helper**: `and(eq(...), eq(...), sql\`AND NOT EXISTS (...)\`)` compiles to `... AND ... AND AND NOT EXISTS (...)` and Postgres rejects it with `syntax error at or near "AND"` (code `42601`). Drizzle's `and()` is responsible for inserting the `AND` between fragments — your `sql` template just contributes the predicate. The empty-fallback `sql\`\`` is correctly skipped by `and()`. Real-world hit: the Phase 1 completion guard in `updateEventStatus` (`backend/trpc/routes/events.ts`) wrote `sql\`AND NOT EXISTS (...)\``, so every Complete-Task press from the creator returned a 500 — the modal closed, no success toast, no error toast (the failure was swallowed as a generic "Failed to update task status" Alert that the user dismissed without noticing), and the task stayed Active. The companion sweep in `_completeExpiredEventsCore` was already correct (`sql\`NOT EXISTS (...)\``); the two diverged because they were written at different times. When in doubt, `console.log(query.toSQL())` once before shipping any non-trivial `sql\`\`` fragment inside `and()` / `or()`.
- **In-app notifications must INSERT inside the same DB transaction as the action they describe**: previously `submitTaskForReview` committed the assignment update inside a tx but called `notifyTaskSubmitted` (which inserts into `notifications`) OUTSIDE the tx, in a `try/catch`. If the server crashed/restarted between the commit and the fan-out (e.g. an `EADDRINUSE` restart), the submission survived but the reviewer's bell stayed silent forever — no retry, no recovery. Real-world hit: NIRMAL submitted to SAJI; bell never appeared, only the inline pending-review pill on the task page exposed the submission. Pattern to use: `tx.insert(notifications).values({...})` inline (with the same dedupe-window check), then dispatch the Expo push OUTSIDE the tx (push is best-effort and a network outage must never roll back a successful submit). Also include the actor id in the dedupe key (`EVENT:<id>:TASK_SUBMITTED:<submitterId>`) so two teammates submitting the same event within the 5-min window don't collide and silently drop the second creator-bell. Always write an audit log for the action itself (`SUBMIT_FOR_REVIEW` / `RESUBMIT_FOR_REVIEW`) so timing can be reconstructed without guessing from `updated_at`. Same fix should be applied to `updateEventStatus`, `approveTask`, `rejectTask`, and the cancel-fan-out as they're touched.
- **Actor-bearing tRPC mutations must use `authedProcedure`**: any mutation that takes an `employeeId`/`reviewerId`/`actorId` from the client must use `authedProcedure` (defined in `backend/trpc/create-context.ts`) and derive the actor from `ctx.employeeId`, not from `input`. Pattern: keep the legacy input field optional, throw `TRPCError({ code: 'FORBIDDEN' })` on mismatch, otherwise use `ctx.employeeId`. See `submitFinanceCollection`, `submitTaskForReview`, `approveTask`, `rejectTask`, and the entire `issues` router (`create`, `updateStatus`, `escalate`) for the canonical shape. Trusting the input field lets any HTTP client impersonate any user. Several older `publicProcedure` mutations still trust input IDs (assignTeam, removeTeamMember, subtask CRUD, etc.) — they should be migrated as they are touched.
- **`window.alert` / `window.confirm` are blocked inside the Replit preview iframe (and many embedded webviews)**: this is the same family of bugs as the documented `Alert.alert([buttons])` failure on RN Web — except the `window.*` variants ALSO swallow your follow-up `router.back()` etc. because the dialog never resolves. Real-world hit on Raise Issue: success path was `window.alert('Issue raised'); router.back();` — the alert never appeared, the user stayed on the form, but the issue WAS created in the DB (silent success looked exactly like silent failure). Fix pattern: never depend on `window.alert/confirm` for control-flow on web. For success, prefer a navigation that itself confirms the action (`router.replace('/(tabs)/issues')` — the new card on the list is the receipt). For confirm-then-act flows, use an in-screen `<Modal>` with explicit Cancel + Confirm `TouchableOpacity`s (and that's also where you collect any required input like resolution notes). The Issues `handleResolveIssue` modal is the canonical shape. Errors are still acceptable to surface via `window.alert` because they're rare AND visibility matters more than polish — but never gate a write on the user dismissing one. Also note `router.back()` itself is unreliable when the screen was opened from a deep link / fresh tab (no history entry) — prefer `router.replace('/(tabs)/<list>')` for any post-submit redirect that has a sensible "list" landing page.
- **Issue display IDs (`ISS-YYYY-MM-NNNN`)** mirror the Task display IDs. Three sources to keep in sync if the format ever changes: (1) `issues.displayId` column in `backend/db/schema.ts` (`varchar(32) unique`, NULLABLE — legacy rows may not have one); (2) `allocateIssueDisplayId()` in `backend/db/issueIdAllocator.ts` (atomic upsert against `issue_id_counters(year, month)`, called OUTSIDE the create-issue tx so a rollback doesn't free the sequence number — same as `allocateTaskDisplayId`); (3) `syncIssueDisplayId()` in `backend/db/migrate-issue-display-id.ts` (idempotent column-add + counter-table-create + backfill, registered in `migrate.ts` so a single `bun run backend/db/migrate.ts` brings new envs up). Frontend cards fall back to `ISS-${id.slice(0,8).toUpperCase()}` when `displayId` is null so legacy / unmigrated rows still show *something*.
- **Self-raised issues need a reporting-manager fallback**: when a manager raises an issue on their OWN task, `event.createdBy === actor`, so the original "fall back to creator" rule produces `escalatedTo = null` and the issue becomes invisible to anyone except the raiser. `issues.create` now walks one step up the reporting chain via `employees.reportingPersNo` → `employees WHERE persNo = reportingPersNo` and uses that manager's id. If the raiser is at the top of the hierarchy (e.g. GM with `reportingPersNo IS NULL`), `escalatedTo` correctly stays null and only the raiser can act — no synthetic escalation to a random admin. `reportingPersNo` is a string staff-id reference (NOT a uuid FK to `employees.id`), so the lookup is `eq(employees.persNo, reportingPersNo)`, not `eq(employees.id, ...)`.
- **Raise Issue authorization model**: `issues.updateStatus` and `issues.escalate` use `loadAndAuthorize()` in `backend/trpc/routes/issues.ts` — only the original raiser, current `escalatedTo`, the task's `createdBy`, the task's `assignedTo`, or any ADMIN/CMD may act. SALES_STAFF / SD_JTO are additionally blocked from resolving issues raised by other employees, even if they can see them. The frontend's `canResolve={role !== 'SALES_STAFF'}` gate is purely cosmetic — the server enforcement is the actual security boundary. Escalation also rejects: target === actor (self-escalation), target === original raiser (loop-back), and any non-existent employee id. Issue create + audit + bell notification all run inside one `db.transaction` with the actor-bearing dedupe key `ISSUE:<id>:<TYPE>:<actorId>` (mirrors the submit-for-review pattern); push dispatch is intentionally outside the tx so a push outage never rolls back a successful issue create.
